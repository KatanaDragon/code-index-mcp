# ТЗ: внутренний каталог индекса на Windows — verbatim-пути `\\?\` ломают создание и запись

Дата постановки: 09.10.2026. Источник — инцидент на рабочей станции Windows
(Kaspersky Endpoint Security активен, песочницы разработки): семь путей демона
(`mdm`×3, `ka-upr_obnovlenie-kontura`×2, `mdm_obnovlenie-kontura`×2) не писали
индекс с 5 октября, вскрылось при первой записи 09.10. Диагностика по живому
узлу, воспроизведение на временных каталогах.

## 1. Что происходит сейчас

Внутренний режим хранения индекса (без `index_dir` в `daemon.toml`, каталог
`<репозиторий>/.code-index`) на этой машине не работает ни в одной фазе записи:

| Репозиторий | Текст ошибки воркера |
|---|---|
| `mdm\src\cf` | `full_reindex: set_bulk_in_progress: … attempt to write a readonly database: Error code 8` — каждая запись с 09.10 11:15 |
| `mdm\src\cfe` | `Storage::open_auto: копирование базы …\.code-index\index.db в память не продвигается: … скопировано 100 страниц из 112` — цикл перезапусков |
| `mdm\tests\exts` | `Ошибка инициализации readonly-схемы: unable to open database file: Error code 14` — и на чтение, и на запись |
| `mdm_obnovlenie-kontura\src\cf` | `каталог …\.code-index не создан: Отказано в доступе. (os error 5)` |

Однократная команда воспроизводит отказ детерминированно, вне контекста демона,
в %TEMP%, на четырёх сборках подряд (20261001-1657, 20261001-1714,
20261002-0917, текущая):

```
bsl-indexer.exe index C:\Users\<user>\AppData\Local\Temp\ci_probe\repo\src\cf
Error: Не удалось создать директорию "\?\C:\Users\…\.code-index": Отказано в доступе. (os error 5)
```

### Замеры, объясняющие поведение

- `CreateDirectoryW` по пути **с** префиксом `\\?\` — отказ (через приложение
  `os error 5`, прямой вызов — `INVALID_NAME (123)`); тот же путь **без**
  префикса создаётся нормально. Отказ нестабилен по коду, но стабилен по факту:
  verbatim-создание ломает фильтр-стек узла (KES/песочницы), обычные пути не
  ломает.
- Чтение по verbatim-пути работает: проверка изменений при старте проходит
  (25 271 файл сверён), `stats --path` читает базу, readonly-слой MCP отдаёт
  данные. Ломается именно **создание** — каталога и сателлитов SQLite
  (`-wal`/`-shm`), поэтому readonly-подключения живут, а каждая запись
  воркера падает.
- Та же `index.db` по обычному пути открывается на запись из стороннего
  процесса (`BEGIN IMMEDIATE` проходит); ACL в порядке (у пользователя Full),
  блокировок нет (Restart Manager — ноль дескрипторов), место на диске есть.

Отсюда картина инцидента: статусы путей висели «готов» неделями (записей не
было), первая же запись после слияния ветки вскрыла readonly. Центральные
`index_dir` на том же узле тем же бинарником работают штатно — при рестарте
демона 09.10 все семь путей переиндексировались в центральные каталоги без
единой ошибки.

### Причина в коде

`std::fs::canonicalize()` на Windows возвращает путь в verbatim-форме с
префиксом `\\?\`, и этот путь дальше используется для всех операций:

- `crates/code-index-core/src/daemon_core/worker.rs:746` — воркер канонизирует
  `entry.path` при старте;
- `crates/code-index-core/src/index_location.rs:40,57` — без `index_dir`
  каталог строится как `root.join(".code-index")` от канонизированного корня;
- `crates/code-index-core/src/cli.rs:1124-1131` — `cmd_index` канонизирует путь
  и вызывает `create_dir_all` по verbatim-каталогу;
- `worker.rs:762` — тот же `create_dir_all` в воркере;
- SQLite открывает БД по verbatim-пути: создание `-wal`/`-shm` отказывает —
  отсюда readonly (8), cantopen (14) и зависшее копирование в память.

Асимметрия, объясняющая «ka-upr зелёные, mdm сломаны»: в ветке с `index_dir`
(`index_location.rs:42-55`) возвращается `dir.clone()` — путь **как записан в
TOML, без канонизации**. Дефект проявляется только там, где путь построен от
`canonicalize()`.

Почему не замечали раньше: чтение по verbatim работает; с 01.10 обходной конфиг
с центральными `index_dir` был снят («пути возвращены», см. комментарий в
`daemon.toml` узла), а правки 01–02.10 касались обработки недоступных баз, не
путей. Отдельные ошибки при этом штатны: миграционная защита
«Есть старый каталог индекса … сначала перенесите его»
(`index_location.rs:51-54`, тест `refuses_old_directory_until_migration`) —
правильное поведение, не дефект.

Попутно обнаружен второй дефект, проявившийся при обходе: **`daemon reload` не
видит смены `index_dir`.** `daemon_core/state.rs:92-118`, `apply_config`
сравнивает наборы `PathBuf` (только пути), `runner.rs:633` передаёт туда только
канонизированные пути — значения полей записи до сравнения не доходят. Смена
каталога индекса в конфиге оставляет воркеры со старым каталогом; в журнале
путь честно попадает в `unchanged`. Обход — скрыть блок пути, перезагрузить,
вернуть, перезагрузить.

## 2. Что требуется

### Требование 1 (главное). Ни один путь, уходящий в ФС или SQLite, не несёт verbatim-префикса

Канонизация — для сравнения и для отсечения симлинков; для файловых операций —
исходная строка из конфига либо канонический путь, приведённый к обычной форме
(без `\\?\` и с корректной обратной конвертацией `\\?\UNC\` в сетевой путь).

- Допустимые реализации: крейт `dunce` (`dunce::simplified` /
  `dunce::canonicalize`) либо собственная упрощалка через `Path::components()` —
  на усмотрение реализации. Обязательное условие: сетевые пути (UNC) не должны
  ломаться.
- Семантика сравнения не меняется: `normalized()` (`index_location.rs:30-37`)
  уже делает lowercase и прямые слеши — оставить как есть.
- Контроль: тексты ошибок, `daemon status`, `get_stats` (`root_path`) не
  содержат `\\?\`.

### Требование 2. Аудит всех точек `canonicalize`

Для каждой точки указать в комментариях: «сравнение» (можно оставить как есть)
или «I/O» (обязательна упрощённая форма). Точки по текущему дереву:

- `daemon_core/worker.rs:746` — I/O, главный виновник;
- `index_location.rs:40` — I/O (от него строится внутренний каталог);
- `cli.rs:1125` (`cmd_index`) — I/O;
- `cli.rs:326, 391, 659, 1462, 1526`, `daemon_core/runner.rs:137, 177, 631,
  747` — разобрать при правке: где сравнение, где операции.

### Требование 3. `reload` считает значимые поля записи изменением конфигурации

`apply_config` должен сравнивать записи целиком (как минимум `index_dir`; далее
по списку влияющих на воркер полей: `language`, `exclude_dirs`,
storage-параметры), а изменённые пути — перезапускать (остановить воркер,
создать заново), а не относить к `unchanged`. Частный случай для приёмки:
смена `index_dir` применяет воркером без цикла «скрыть/вернуть блок».

### Требование 4. Диагностика на случай иного окружения

При отказе `create_dir_all` / открытия БД добавлять в сообщение подсказку:
если путь в verbatim-форме и отказ похож на фильтр (ACCESS_DENIED /
INVALID_NAME) — упомянуть, что рабочий путь должен быть без `\\?\`. Пункт
страховочный: после требования 1 таких отказов быть не должно.

## 3. Проверка приёмки

Обязательная часть — на узле, где воспроизводится (Windows, KES активен,
репозитории mdm/ka-upr):

1. Свежий временный каталог-«репозиторий», в `daemon.toml` демона путь без
   `index_dir` → демон индексирует во внутренний `.code-index`: в журнале нет
   `\\?\`, каталог создан, первичная запись прошла (было: `mkdir` — os error 5).
2. `bsl-indexer.exe index <временный каталог>` — создаёт `.code-index` и
   индексирует без ошибки (было: детерминированный отказ).
3. `get_stats` / состояние демона: `root_path` и пути ошибок — без префикса.
4. Существующие центральные конфигурации (`ka-upr` и прочие с `index_dir`) —
   статусы «готов», без переиндексации, поведение не изменилось.
5. Миграционная защита жива: центральный `index_dir` + существующий
   `.code-index` → отказ «сначала перенесите его», тест
   `refuses_old_directory_until_migration` зелёный.
6. Смена `index_dir` у существующего пути + `daemon reload` → воркер
   перезапущен с новым каталогом; в выводе reload путь в `changed`/`added`, а
   не в `unchanged`.
7. Юнит-тесты: (а) на Windows построенный внутренний каталог не содержит
   verbatim-префикса; (б) `apply_config`/reload детектирует смену `index_dir`.
8. Весь workspace зелёный.

## 4. Чего делать не надо

- Не «чинить» переводом всех путей на центральные индексы по умолчанию: выбор
  расположения — решение узла, внутренний режим остаётся поддерживаемым
  дефолтом (`CHANGELOG`, v1.0.1: «без настройки остаётся прежний .code-index»).
- Не отказываться от миграционного запрета «Есть старый каталог индекса» и от
  теста на него.
- Не менять семантику `normalized()` — сравнения путей работают.
- Не лечить отдельно «копирование базы в память не продвигается» и «readonly
  при записи»: это следствия требования 1. Если после снятия verbatim что-то
  останется — отдельная задача с новым разбором.

## 5. Порядок выкатки

Стандартный цикл не сокращать: тесты workspace → локальная сборка и деплой
через mcp-supervisor → smoke на живой базе → musl-сборка → раскатка. Обязательное
дополнение: smoke по пунктам 1–3 приёмки — именно на Windows-узле с KES, где
дефект воспроизводился (mdm/ka-upr); на узлах без фильтр-стека дефект не
проявлялся и там регресс не виден. После раскатки — сверка статусов всех путей
демона (готовы/ошибки) на обоих узлах.
