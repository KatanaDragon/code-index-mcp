# ТЗ: текстовый поиск по всем категориям файлов одним вызовом

Дата постановки: 07.09.2026. Источник — работа агента по XML-выгрузке КА (Комплексная
автоматизация, 125 107 файлов): при оценке полноты точек для переименования объекта
`Catalog.КРБ_Тягачи` первая же попытка «найти имя везде» дала 4 файла из 10.

## 1. Что происходит сейчас

XML выгрузки Конфигуратора индексируется двумя разными путями (`daemon_core/worker.rs`,
ветка `FileCategory::Text`):

| Файлы | Куда попадают | Язык | Чем ищутся |
|---|---|---|---|
| `Configuration.xml`, `Form.xml`, `Rights.xml`, md, json, yaml | `text_contents` (+ FTS) | `text` | `grep_text`, `search_text` |
| объектные XML (`Catalogs/X.xml`, `Documents/X.xml`, регистры, `Subsystems/**.xml`) — парсер `Xml1CParser` нашёл реквизиты | `file_contents` (zstd) | `xml_1c` | `grep_code(language="xml_1c")` |
| `ConfigDumpInfo.xml` | не индексируется (проектно, `categorize_file`) | — | только внешний grep |

Решение само по себе разумное: у объектных XML есть структура, из неё строятся
`metadata_objects`, `data_links`, `variables`; текстовый индекс для них не нужен. Но у
пользователя инструментов картина другая — он видит два «грепа» и ни один не отвечает
на вопрос «где в выгрузке встречается это имя»:

```
grep_text(repo="ka", pattern="КРБ_Тягачи", path_glob="**/*.xml")   → 4 файла
grep_code(repo="ka", pattern="КРБ_Тягачи", language="bsl")         → 1 файл
grep_code(repo="ka", pattern="КРБ_Тягачи", path_glob="**/*.xml")   → 5 файлов (только xml_1c)
grep_code(repo="ka", pattern="КРБ_Тягачи", language="xml_1c")      → 5 файлов
git grep -l -F КРБ_Тягачи -- src exts                              → 12 файлов (12 с; 11 в src + 1 в exts)
```

Полный ответ индекса по `src` — объединение трёх вызовов: `grep_text` (4 файла),
`grep_code(language="xml_1c")` (5) и `grep_code(language="bsl")` (1) — 10 файлов из 11
(одиннадцатый — `ConfigDumpInfo.xml`, исключён намеренно). Чтобы это знать, надо прочитать
`file_types.rs` и `worker.rs`. Описание `grep_code` прямо отсылает «для xml/md/yaml —
grep_text», и агент честно идёт туда — и получает неполный ответ, неотличимый от честного
«в остальных файлах имени нет». Замер на КА: в `files` 54 317 файлов категории `text`
(5,5 ГБ), 34 311 — `xml_1c` (254 МБ), 25 975 — `bsl`.

### Где именно теряется полнота

- `grep_text` → `storage.grep_text_filtered` читает только `text_contents`.
- `grep_code` → `storage.grep_code_filtered` читает только `file_contents`; фильтр
  `path_glob="**/*.xml"` без `language` отбирает те же `xml_1c`, потому что `Form.xml` и
  `Configuration.xml` в этой таблице отсутствуют.
- Подсказки при нуле совпадений (`grep_code_empty_hint`, `HINT_GREP_TEXT_EMPTY`) не говорят,
  что часть XML лежит в другой категории.

Это не ошибка индексации — всё содержимое в базе есть и `oversize` у `xml_1c` равен нулю.
Это разрыв между устройством хранения и вопросом, который задаёт пользователь.

## 2. Что нужно

Один вызов, который ищет подстроку или regex **по всему индексированному тексту репозитория**
независимо от категории хранения, с тем же форматом ответа, что у `grep_code`/`grep_text`.

### 2.1. Вариант А (рекомендуемый): параметр `scope` у `grep_code` и `grep_text`

Оба инструмента получают необязательный параметр:

```
scope: "code" | "text" | "all"
```

- у `grep_code` по умолчанию `"code"`, у `grep_text` — `"text"` — поведение и ответы
  существующих вызовов не меняются;
- `scope="all"` выполняет оба поиска (`grep_code_filtered` + `grep_text_filtered`) с одними
  `regex`/`pattern`, `path_glob`, `language`, `limit`, `context_lines` и сливает результат;
- `language` при `scope="all"` фильтрует только код (у текстовых файлов языка нет), а
  `path_glob` действует на обе категории;
- ответ — тот же `{files, shown, limit, truncated}` (`compact_text_matches`), файл из любой
  категории — ключ в `files`; дополнительно `by_category: {"code": N, "text": M}` (число
  файлов), чтобы было видно, откуда пришли находки;
- `limit` — общий на два поиска; `truncated=true`, если обрезался хотя бы один; поиск по
  коду выполняется первым (он дешевле: `xml_1c` в 20 раз меньше `text` по объёму);
- `files_unreadable` суммируется (`annotate_unreadable`).

Один параметр вместо нового инструмента: в `tools/list` уже 32 инструмента, а описания
`grep_code`/`grep_text` и так объясняют разницу между ними — проще добавить фразу «нужно всё
сразу — `scope="all"`».

### 2.2. Вариант Б: новый инструмент `grep_all`

Те же параметры, что у `grep_code`, минус `scope`. Плюс — не трогает сигнатуры существующих
инструментов и federation-протокол; минус — 33-й инструмент и третье описание про грепы,
которое модели придётся сопоставлять с двумя другими. Оставлен как запасной, если `scope`
невозможно провести через `dispatch_remote` без ломки старых нод (см. §4).

### 2.3. Не делать

- **Не переводить `xml_1c` в двойную индексацию** (`is_dual_indexed_language`), чтобы
  объектные XML попадали и в `text_contents`. Это +254 МБ дублированного текста на КА, вторая
  копия в FTS и удвоенная запись при каждом изменении объекта — ради того, чтобы один
  инструмент видел то, что уже видит другой.
- **Не индексировать `ConfigDumpInfo.xml`**: решение из `categorize_file` верное (опись uuid и
  хешей версий, поиск по ней бессмысленен, размер десятки МБ). В ответе `scope="all"` при
  `path_glob`, покрывающем корень, достаточно подсказки: «ConfigDumpInfo.xml не индексируется».

## 3. Подсказки и описания — независимо от варианта

Даже без нового поведения полноту спасают три правки текста:

1. Описание `grep_code`: «Объектные XML выгрузки 1С (`Catalogs/X.xml`, документы, регистры,
   подсистемы) хранятся как код с `language="xml_1c"` — ищите их здесь с этим языком;
   `Configuration.xml`, `Form.xml`, `Rights.xml` — категория text, см. `grep_text`».
2. Описание `grep_text`: зеркальная фраза про `xml_1c`.
3. `grep_code_empty_hint` при `language="bsl"` или `path_glob="**/*.xml"` и `HINT_GREP_TEXT_EMPTY`
   при `path_glob` на xml: «часть XML выгрузки лежит в другой категории — повторите с
   `language="xml_1c"` / через `grep_text`» (или «`scope="all"`», когда он появится).

Стоимость — строки текста; эффект — агент перестаёт делать вывод «имени нет» по половине
данных.

## 4. Ограничения и совместимость

- **Federation.** `GrepCodeParams`/`GrepTextParams` пересылаются на удалённую ноду как есть
  (`dispatch_remote`); нода на прежней сборке поле `scope` проигнорирует и вернёт результат
  одной категории. Как с `pattern` (сводится к `regex` до пересылки): при `scope="all"` и
  удалённом репо выполнять два запроса (`grep_code` и `grep_text`) с локальной стороны и
  сливать здесь — тогда старые ноды работают без изменений.
- **Кэш ответов.** Ключ кэша строится из параметров — `scope` должен в него входить, иначе
  ответ `scope="all"` перезапишет ответ `scope="code"` с теми же остальными полями.
  `_meta.dependent_files` — объединение обоих поисков, чтобы инвалидация по файлу работала для
  обеих категорий.
- **Бюджет ответа.** `GREP_TOTAL_BYTES_CAP` применяется к сумме; при обрезке в ответе должно
  быть видно, какая категория обрезана (`truncated_by_category`), иначе повторяется исходная
  проблема — неполный ответ без признака неполноты.
- **Порядок в `files`.** `compact_text_matches` сортирует по пути (`BTreeMap`) — категории
  перемешаются по алфавиту путей; это ожидаемо, разделять их не нужно, `by_category` даёт
  счётчики.

## 5. Приёмка

На выгрузке КА (или любой конфигурации с `Configuration.xml`, формами и ролями):

1. `grep_code(pattern="КРБ_Тягачи", scope="all")` возвращает 10 файлов: 5 из категории `xml_1c`
   (справочник, два документа, регистр, подсистема), 4 `text` (`Configuration.xml`, `Form.xml`
   обработки, два `Rights.xml` ролей) и 1 `bsl` (модуль формы); `by_category` = `{"code": 6,
   "text": 4}` и совпадает с суммой `grep_code(language="xml_1c")` + `grep_code(language="bsl")`
   + `grep_text(path_glob="**/*.xml")`.
2. Тот же вызов без `scope` (и `grep_text` без `scope`) возвращает ровно то, что до правки —
   существующие тесты `grep_code`/`grep_text` проходят без изменений.
3. `scope="all"` с `limit=3` даёт `truncated=true` и `truncated_by_category`, показывающий, где
   обрезано; `shown` равно 3.
4. Удалённый репо на сборке без `scope`: `scope="all"` отдаёт объединение двух категорий
   (запросы выполняются с локальной стороны).
5. `grep_code(pattern="…", language="bsl")` с нулём совпадений отдаёт подсказку про `xml_1c` /
   `scope="all"`; `grep_text(path_glob="**/*.xml")` с нулём — про объектные XML в коде.
6. `ConfigDumpInfo.xml` в ответах не появляется, подсказка про его исключение есть при
   `scope="all"` без сужающего `path_glob`.

## 6. Что не входит

- Индексация макетов `Template.xml` (MXL) и `ConfigDumpInfo.xml`.
- Поиск по псевдонимам таблиц в запросах (это `find_references`, не grep).
- Изменение схемы хранения (`file_contents`/`text_contents`) — правка только на уровне
  инструментов и подсказок.
