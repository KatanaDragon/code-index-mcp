## 2. Что нужно

### 2.1. Разбор комментария: метатеги отдельно от прозы, без лимита

`terms.rs`:

- `extract_leading_comment` возвращает не строку, а структуру `LeadingComment { prose: String,
  tags: Vec<String>, depends: Vec<String>, len_chars: usize }`:
  - строки вида `@<тег> <значение>` (после снятия `//` и пробелов; регулярка одна —
    `^@(\w+)\s+(.+)$`, как в `code-docs`) в прозу **не попадают**; `@tags` делится по запятой,
    `@depends` — по точке с запятой, значения — `fold_text` + `trim`; прочие теги (`@layer`,
    `@security`, `@todo`, `@example`) игнорируются — в поисковые термы они шума добавят больше,
    чем сигнала;
  - `prose` — остальные содержательные строки, обрезка до 240 символов **остаётся** (термы — сигнал
    для FTS, не полнотекст); `len_chars` — длина всего комментария до обрезки (для `comment_len`).
- `build_terms(name, object, synonym, comment: &LeadingComment, module_tags: &[String])`: порядок
  фраз — теги процедуры, слова имени, объект, синоним, проза, теги модуля; дубли схлопываются как
  сейчас. Теги — отдельные фразы через запятую, чтобы триграммы матчили слово целиком («весы», а не
  «…службе весов из…»).
- `MECH_SIGNATURE` → `mech:v2`.
- Тесты (в `mod tests` рядом с `comment_extraction`, `build_terms_full_and_dedup`): теги за
  границей 240 символов попадают в структуру; `@`-строки отсутствуют в `prose`; `@security` не
  создаёт термов; ё→е и регистр в тегах; комментарий только из тегов (`prose` пуста,
  `len_chars` > 0); порядок фраз и дедупликация с тегами модуля.

### 2.2. Колонки в `procedure_enrichment` и вес тегов в FTS

`schema.rs`, `migrate_extensions` через `ensure_column`:

- `tags TEXT NOT NULL DEFAULT ''` — теги процедуры через запятую (как в исходнике, после
  `fold_text`);
- `comment_head TEXT NOT NULL DEFAULT ''` — первая содержательная строка комментария, до 160
  символов (то, что агенту показать в выдаче вместо всего `terms`);
- `comment_len INTEGER NOT NULL DEFAULT 0` — длина комментария до обрезки; `0` — описания над
  процедурой нет.

Все три пути заполнения (§1, строки «три пути») пишут новые колонки; LLM-строки (`signature`
не `mech:%`) не трогаются — у них колонки остаются по умолчанию, и аудит §2.4 обязан фильтровать
`signature LIKE 'mech:%'`.

FTS: вторая колонка `tags` в `fts_procedure_enrichment` и ранжирование с весом —
`ORDER BY bm25(fts_procedure_enrichment, 1.0, 4.0)` (проза 1, теги 4; число подобрать на замере
§5.3, 4 — стартовое). Миграция по образцу `ensure_trigram_tokenizer`: DDL в `sqlite_master` без
слова `tags` → `DROP` + `CREATE VIRTUAL TABLE … (terms, tags, content=…, tokenize='trigram')` +
`rebuild`; триггеры `PE_FTS_TRIGGERS_DDL` переписываются на две колонки (снять и поставить заново в
той же миграции — они пересоздаются `IF NOT EXISTS`, старые надо `DROP TRIGGER`). Запрос в
`search_terms`: `MATCH` без указания колонки ищет по обеим.

### 2.3. Шапка модуля: таблица `module_enrichment`

`schema.rs`, в `SCHEMA_EXTENSIONS`:

```sql
CREATE TABLE IF NOT EXISTS module_enrichment (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    repo TEXT NOT NULL,
    path TEXT NOT NULL,          -- repo-relative путь .bsl, как files.path
    header TEXT NOT NULL,        -- проза шапки, до 1000 символов
    tags TEXT NOT NULL DEFAULT '',
    depends TEXT NOT NULL DEFAULT '',
    signature TEXT NOT NULL,
    updated_at INTEGER NOT NULL DEFAULT 0,
    UNIQUE(repo, path)
);
CREATE INDEX IF NOT EXISTS idx_me_path ON module_enrichment(repo, path);
```

`terms.rs`: `extract_module_header(lines) -> Option<ModuleHeader { prose, tags, depends }>`:

- идём от начала файла (BOM снят ядром), пропуская пустые строки и рамки `////`/`//==`; собираем
  строки `//`; останавливаемся на первой не-комментарной строке;
- блок **не** шапка, а комментарий первой процедуры, если он без пустой строки переходит в
  `Процедура`/`Функция`/`&Аннотация` — тогда `None`; шапка принимается, если после блока идёт
  пустая строка, `#Область`, `#Если`, `Перем` или конец файла;
- метатеги — тем же разбором, что в §2.1; `prose` до 1000 символов;
- тесты: КА-образец `КРБ_ИнтеграцияВесов` (рамка, «Общий модуль…», абзац, `@layer`, `@tags`) →
  `tags = ["весы","служба","настройки","интеграция"]`; файл, начинающийся с `#Область`, → `None`;
  комментарий процедуры без шапки → `None`; шапка + пустая строка + процедура → шапка; пустой
  модуль (3 байта) → `None`.

Заполнение — теми же тремя путями: сборщик `on_parsed` (у него уже есть `ctx.content`) кладёт
строку в temp-staging `_module_header_staging` и `write` переносит в таблицу; `full_scan` —
после термов процедур (второго чтения файла не нужно: `lines` уже в памяти, см. цикл в
`index_procedure_terms`); инкремент — в `update_procedure_terms_for_file` (удаление строки пути,
вставка заново; удалённый файл — только удаление). Теги модуля из этого же разбора передаются в
`build_terms` экспортных процедур файла (§2.1, `module_tags`) — так ключевые слова шапки находят
процедуры модуля, а отдельного поиска по модулям не нужно.

### 2.4. Выдача агенту

- `search_terms` (`tools/search_terms.rs`): в каждом попадании дополнительно `tags`,
  `comment_head`, `module_tags` (по `module_enrichment` через путь из `proc_key`); существующие
  поля не меняются. Описание инструмента: «…комментарий над процедурой и метатеги `@tags` (вес
  выше прозы), теги шапки модуля»; подсказка на пустом ответе — без изменений.
- `get_object_profile` (`tools/get_object_profile.rs`): в секции `modules` у каждого модуля —
  `header` (первая строка `prose`, до 160 символов) и `tags`, когда строка в `module_enrichment`
  есть; в компактной форме (`by_type`) — только `tags`. Описание инструмента — одно предложение
  про шапку.
- `bsl_sql` (`tools/bsl_sql.rs`): в перечень таблиц описания — `module_enrichment(path, header,
  tags, depends)` и новые колонки `procedure_enrichment(tags, comment_head, comment_len)`.
- Аудиты отдельным инструментом не делаются — шаблоны `bsl_sql` в скилл контура `1c-code-index`
  (раздел 4):

```sql
-- экспортные процедуры своих общих модулей без описания над объявлением
SELECT e.path, e.name FROM exported_procs e
LEFT JOIN procedure_enrichment p
  ON p.repo = e.repo AND p.proc_key = e.path || '::' || e.name AND p.signature LIKE 'mech:%'
WHERE e.path LIKE 'CommonModules/КРБ_%' AND COALESCE(p.comment_len, 0) = 0
ORDER BY e.path, e.name;

-- свои модули с кодом без шапки
SELECT m.code_path FROM metadata_modules m
LEFT JOIN module_enrichment me ON me.repo = m.repo AND me.path = m.code_path
WHERE m.object_name LIKE 'КРБ_%' AND me.id IS NULL;
```

(второй запрос уточнить по факту: пустые модули в `metadata_modules` отсеять по `files.lines_total`).

### 2.5. Пересборка термов при смене подписи

Инкремент переписывает термы только изменённых файлов, поэтому после обновления бинарника КА
жил бы с `mech:v1` до следующей полной индексации. Требование: при открытии базы расширением
(там же, где `migrate_extensions`) — если есть строки `signature = 'mech:v1'` при текущей `mech:v2`,
выполнить **терм-проход** (`index_procedure_terms` + шапки модулей) без переиндексации метаданных
и графов. Оценка: чтение 26 000 `.bsl` и вставка 691 228 строк — десятки секунд, не 394 с полной
индексации (замер записать в CHANGELOG). Пока проход идёт, `health` отвечает «не готов», как при
индексации. Запасной путь — `bsl-indexer index --config daemon.toml` целиком.
