## 2. Цель

Поднять попадание в нужную процедуру по запросу «на человеческом языке» (там, где точное написание идентификатора неизвестно) — и **знать в цифрах**, насколько подняли.

Критерий успеха этапа в целом: на закрытом тестовом наборе recall@10 ≥ 0.80 при сохранении времени ответа ≤ 1 с локально.

Явно **не** цель: заменить лексические каналы (`grep_code`, `find_references`, FTS по термам). Векторный канал — дополнение, которое сливается с ними в одной выдаче; лексика ловит то, что векторы промахивают, и наоборот.

---

## 3. Принцип очерёдности

Порядок жёсткий, шаги нельзя переставлять:

```
A. Эвал-набор  →  B. 5b на готовой модели  →  C. Гибрид RRF  →  D. Замер
                                                                    ↓
                                          решение: хватит / реранкер / дообучение
```

Дообучение эмбеддера стоит в конце не из осторожности, а по устройству задачи: в архитектуре зафиксирован инвариант `embedding_signature` — смена модели требует полной переиндексации (~313k процедур). Каждая итерация обучения тянет за собой переиндексацию, поэтому итерации должны быть редкими и осмысленными.

## 4. Этап A — эвал-набор (делается ПЕРВЫМ)

Без него все последующие шаги неизмеримы.

### Состав

200–300 пар «вопрос → эталонная процедура (`proc_key`)». Делится на:

* **dev** (~100) — на нём крутим настройки, смотрим сколько угодно;
* **test** (~150) — **вскрывается один раз на этапе D**. Каждый повторный просмотр обесценивает набор.

### Источники вопросов (по убыванию ценности)

1. **Реальная история задач по КА** — `docs/<Номер>/ТЗ.md`. Формулировки из ТЗ — это ровно то, как ставится задача до знакомства с кодом.
2. **Логи обращений агента** к `search_terms` / `bsl_sql` за прошлые сессии + какая процедура в итоге оказалась нужной. Самый честный сигнал: так формулирует агент, а не человек-разметчик.
3. **Ручная постановка** по разделам конфигурации, которые не покрыты первыми двумя (чтобы не перекосить набор в сторону недавних задач).

### Правила, защищающие от самоподтверждения

Это критично — плохо собранный эвал хуже, чем никакого, потому что даёт ложную уверенность.

* Вопрос формулируется **до** того, как автор увидел выдачу системы.
* Эталонный `proc_key` определяется чтением кода, а не выбором из топа выдачи.
* Вопросы **не генерируются** той же LLM, что делает `enrich` — иначе меряем согласие модели с самой собой.
* Формулировка не должна содержать точное имя процедуры. Если содержит — это тест на `find_symbol`, а не на семантику; такие случаи выносим в отдельную подгруппу.
* Допускается несколько эталонов на вопрос (функционал размазан по модулям) — тогда засчитываем попадание любого.

### Метрики

* `recall@10` — основная;
* `MRR@10` — чувствительна к позиции, показывает качество ранжирования;
* `recall@50` — потолок для реранкера: выше него реранкер не прыгнет;
* доля запросов с пустой выдачей.

### Артефакты

* `eval/queries-dev.jsonl`, `eval/queries-test.jsonl` — `{query, expected: [proc_key], tags: []}`;
* `scripts/eval_search.py` — прогон набора через MCP-инструменты, печать метрик по каналам.

### Выход

Замер **текущего** `search_terms` на dev-наборе. Это и есть baseline. Возможно, он окажется достаточным — тогда этапы B–F не нужны, и мы сэкономили месяцы.

## 5. Этап B — реализация 5b на готовой модели

Без дообучения. Цель — рабочий второй канал.

### Схема

```sql
CREATE TABLE IF NOT EXISTS embedding_meta (
    key TEXT PRIMARY KEY,
    value TEXT
);
-- 'embedding_signature' = 'openai_compatible:bge-m3:1024'

CREATE VIRTUAL TABLE procedures_vec USING vec0(
    proc_key TEXT PRIMARY KEY,
    embedding float[1024]
);
```

Вектор строится **только по сырому телу процедуры**. Обоснование — в архитектурном документе: подмешивание `terms` в вектор рассинхронизирует пространство смыслов между обогащёнными и необогащёнными процедурами.

### Правки по файлам

| Файл | Что |
|---|---|
| `crates/bsl-extension/Cargo.toml` | фича `embeddings = ["dep:reqwest", "dep:sqlite-vec"]` |
| `crates/bsl-indexer/Cargo.toml` | проброс `embeddings = ["bsl-extension/embeddings"]` |
| `crates/code-index-core/src/daemon_core/config.rs` | `EmbeddingsConfig` по образцу `EnrichmentConfig:336` |
| `crates/bsl-extension/src/schema.rs` | DDL `embedding_meta`; `procedures_vec` создаётся только под фичей |
| `crates/bsl-extension/src/embeddings/` | `mod.rs`, `signature.rs`, `client.rs`, `batch.rs`, `cli.rs` — калька с `enrichment/` |
| `crates/bsl-extension/src/embeddings/search.rs` | поиск ближайших по `procedures_vec` — **внутренняя функция, не MCP-инструмент** (см. §6) |
| `crates/bsl-extension/src/tools/search_terms.rs` | служебный параметр `mode` (см. §6); на этапе B `auto` ≡ `fts`, наблюдаемое поведение не меняется |

Структура `enrichment/` копируется намеренно: `signature`/`prompt` вне фичи (нужны тестам без сети), `client`/`batch`/`cli` — под фичей, плюс stub с внятной ошибкой для сборок без неё (`enrichment/mod.rs:31-38`).

### Модель

Старт — `bge-m3` (568M, XLM-RoBERTa, 1024 dim, контекст 8192) через Ollama или llama-server. Причины: приличный русский, открытые веса, есть парный реранкер `bge-reranker-v2-m3` для этапа E.

Инвариант сигнатуры: при несовпадении `embedding_signature` — отказ старта с требованием `bsl-indexer reindex`. Никакого fallback: векторы разных моделей лежат в разных пространствах, молчаливая подмена даст правдоподобный мусор.

### Прочее

* LRU-кеш эмбеддингов запросов (~1000 записей, ~4 МБ) — запросы агента повторяются.
* Процедуры > 16k символов: обрезка по `char`, не по байтам — на кириллице побайтовая резка рвёт UTF-8 (грабли уже описаны в `enrichment/prompt.rs:38-47`).
* Инкрементальность по `proc_hash_fast`, как у enrichment.

### Выход

Векторный канал работает и замеряется через `search_terms` с `mode=vector`. Число MCP-инструментов не растёт, выдача по умолчанию не меняется — этап B нейтрален для текущих пользователей. Замер на dev-наборе. Ожидаемое время полного прохода локально — 3–6 часов.

## 6. Этап C — гибрид как поведение `search_terms` по умолчанию

Векторы и FTS ошибаются по-разному, и это главный источник выигрыша — часто больший, чем от дообучения.

### Решение

**Отдельного MCP-инструмента для гибрида нет. `semantic_search` в `tools/list` не выставляется.** Векторный канал — внутренняя функция, которую `search_terms` подмешивает сам; для агента инструмент остаётся один и с тем же именем.

Обоснование:

* Стенд 08.09.2026 показал, что модель не идёт в нужный инструмент даже по прямому хинту в пустом результате — пришлось встраивать маршрут в текст ответа (`tools/bsl_sql.rs:251-255`, `386-402`). Тринадцатый инструмент повторил бы эту историю.
* Описание каждого инструмента висит в контексте постоянно, независимо от того, зовут его или нет. Инструмент, который зовут в 5% случаев, стоит контекста 100% времени.
* Агенту незачем выбирать канал поиска: правильный выбор — «спроси по смыслу», а каким индексом это обслужено, его не касается.

### Формула

Reciprocal Rank Fusion:

```
score(doc) = Σ  1 / (k + rank_канал(doc)),   k = 60
```

Каналы: FTS по `procedure_enrichment.terms`; FTS ядра по именам и телу (`search_function` / `grep_body`); векторный по `procedures_vec`.

RRF выбран вместо взвешенной суммы сознательно: не требует калибровки шкал между FTS-score и косинусом и не разъезжается при смене модели.

### Деградация — обязательное требование

`search_terms` уже работает на КА и отвечает за 1–30 мс без сети. Ни одно из условий ниже не должно менять его наблюдаемое поведение по сравнению с сегодняшним:

* секции `[embeddings]` нет в `daemon.toml`;
* `enabled = false`;
* `procedures_vec` пуста или отсутствует (сборка без фичи `embeddings`);
* embedder не отвечает или отвечает дольше таймаута.

Во всех случаях — тихий откат на чистый FTS и ровно тот же ответ, что сегодня. Ошибка embedder'а пишется в лог, но не просачивается в MCP-ответ и не роняет запрос. Таймаут на embed запроса — 500 мс; по истечении отдаём FTS-результат.

Единственное исключение из «тихо»: несовпадение `embedding_signature` — это отказ старта демона, а не деградация запроса (инвариант §5). Разница принципиальна: недоступный embedder означает «канала нет», несовпавшая подпись означает «данные в индексе не те, чем кажутся».

### Служебный параметр `mode`

Для замеров §7 нужно изолировать каналы, не заводя инструментов:

`mode`: `auto` (по умолчанию) | `fts` | `vector` | `hybrid`

* `auto` — гибрид, если векторный канал доступен, иначе FTS;
* остальные — принудительно, для стенда.

В `input_schema` помечается как служебный, с явным «не задавать в обычной работе — значение по умолчанию правильное».

### Изменения в ответе

`score` меняет природу: было — FTS-ранг (bm25), стало — RRF-score. Шкалы несравнимы; абсолютные значения между версиями сопоставлять нельзя, порядок сортировки — можно. Потребителей, завязанных на величину `score`, в контуре нет, но зафиксировать это надо явно.

Добавляется `channels: ["fts", "vec"]` — какими каналами найдена запись. Это и диагностика на стенде, и дешёвый сигнал при разборе промахов.

`proc_key` и `terms` остаются как есть. У записей, найденных только векторным каналом, `terms` может быть пустым — это штатно, а не признак сбоя.

### Описание инструмента

`SearchTermsTool::description()` **переписывается, а не дополняется**. Текущий текст (`search_terms.rs:34-50`) подробно объясняет механику термов: CamelCase-сплит, синонимы, триграммы. После гибрида эта механика перестаёт быть всей правдой, и при этом модели она в таком объёме не нужна — а платим за неё в каждом запросе.

Новый текст отвечает на четыре вопроса и больше ни на какие: что ищет, как формулировать (1–3 слова по смыслу), что возвращает, куда идти за телом. Устройство каналов внутрь описания не выносим.

Бюджет: не длиннее текущего описания.

### Правки по файлам (дополнительно к §5)

| Файл | Что |
|---|---|
| `crates/bsl-extension/src/tools/search_terms.rs` | RRF-слияние, `mode`, деградация, новое описание, `channels` в ответе |
| `crates/bsl-extension/src/tools/semantic_search.rs` | **не создаётся** |
| `crates/bsl-extension/src/processor.rs` | число инструментов не меняется — счётчик в тесте (`processor.rs:316`) править не нужно |
| `1c-agent-contour/skills/1c-code-index/SKILL.md` | обновить раздел про `search_terms`: гибрид по умолчанию, `channels` в ответе, `score` несравним между версиями |
| копии скилла | синхронизировать `KA/.claude` и `~/.claude` — иначе агент будет работать по старому описанию |

Последние две строки не косметика: скилл `1c-code-index` — основной источник знаний агента об этом инструменте, и рассинхрон скилла с поведением даст худший результат, чем отсутствие гибрида.

## 7. Этап D — замер и точка принятия решения

Вскрываем **test**-набор. Один раз. Сравниваем четыре конфигурации:

| # | Конфигурация | Как снимается |
|---|---|---|
| 1 | только FTS (baseline — сегодняшнее поведение) | `mode=fts` |
| 2 | только векторы | `mode=vector` |
| 3 | гибрид RRF | `mode=hybrid` (= `auto` при доступном embedder) |
| 4 | гибрид + реранкер (если этап E сделан) | `mode=hybrid` + rerank |

Все четыре снимаются одним инструментом через служебный `mode` (§6) — стенд не зависит от того, что выставлено в `tools/list`.

Развилка по recall@10 гибрида:

* **≥ 0.80** — цель достигнута. Останавливаемся. Дообучение не нужно.
* **0.65–0.80** — идём на этап E (реранкер). Дообучение би-энкодера — нет.
* **< 0.65** — разбираемся *почему*, и только потом решаем. Низкий recall@50 означает, что теряем на извлечении (нужен этап F); высокий recall@50 при низком recall@10 — теряем на ранжировании (достаточно этапа E).

Этот последний критерий важнее остальных: он отделяет проблему извлечения от проблемы ранжирования, а лечатся они разными средствами.

## 8. Этап E — cross-encoder реранкер

Дешевле и обычно результативнее дообучения би-энкодера.

`bge-reranker-v2-m3` поверх топ-50 гибрида. Отличия от этапа F в нашу пользу:

* **не требует переиндексации** — работает на лету поверх выдачи, итерации быстрые;
* обучается на меньшем объёме данных;
* даёт больший прирост именно в топе (что нам и нужно: агент смотрит первые 5–10).

Цена: +100–300 мс на запрос локально. Приемлемо.

Сначала — готовый реранкер без дообучения. Дообучение реранкера (если понадобится) — на парах из этапа F.1, но без всех издержек переиндексации.

## 9. Этап F — дообучение би-энкодера

**Только если этап D дал recall@50 < 0.7**, то есть теряем на извлечении.

### F.1 Данные

Источники пар «запрос → процедура»:

| Источник | Как получить | Качество |
|---|---|---|
| Логи `search_terms` + фактически использованная процедура | начать логировать **сейчас**, независимо от остальных этапов | высшее |
| LLM-генерация вопросов к процедуре | расширить промпт `enrichment/prompt.rs`: кроме терминов просить 3–5 вопросов | высокое |
| Комментарий-шапка → тело процедуры | из индекса, бесплатно | среднее, шумно |
| Синоним объекта → процедуры из `get_data_links` | из индекса, бесплатно | среднее |

Объём: 20–50k качественных пар достаточно. 313k × 3 — избыточно и дорого.

**Hard negatives — критично.** Случайные негативы почти не двигают метрики. Майнить базовой моделью: топ-10 на запрос минус эталон. Без этого шага дообучение можно не начинать.

### F.2 Обучение

* LoRA (r=16–32) на attention, не full fine-tune.
* Лосс `MultipleNegativesRankingLoss` (InfoNCE).
* Большой батч обязателен — негативы берутся из батча. Отсюда gradient checkpointing + GradCache; при батче 8 результата не будет.
* Одна карта 24 ГБ, часы.

### F.3 Издержки

* Новая сигнатура → полная переиндексация 313k процедур на каждую итерацию.
* Нужен held-out от test-набора, иначе переобучение на эвал.
* Модель становится вашим активом с собственным жизненным циклом: хранение весов, воспроизводимость сборки, привязка версии модели к версии индекса.

## 11. Что в эту работу не входит

* Дообучение **генеративной** модели на правилах и скиллах контура — отдельно разобрано и признано нецелесообразным: правила это факты, а не стиль; они меняются быстрее цикла обучения; половина контура — детерминированные скрипты.
* Замена `search_terms` векторным каналом.
* Гибрид нескольких эмбеддинг-моделей с автоматическим fallback — не реализуем по природе векторных пространств.
* Интеграция с `bsl-agent` на VM RAG (PostgreSQL + pgvector). Это отдельный стек; решение о слиянии или разделении — после этапа D.
