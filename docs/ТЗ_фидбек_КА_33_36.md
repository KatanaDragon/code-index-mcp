## 2. П3. Подсказка `daemon_offline` называет несуществующую команду и не различает «демон убит»

### Факт

Фидбек 33–36, «MCP и инструменты» п. 1: у всех четырёх исполнителей `daemon_offline` на 127.0.0.1:52012; вызывателей искали grep'ом. Текст отказа советует `'code-index daemon run'`, а на машине индексатор — `bsl-indexer.exe` (`C:\Rusin\ka-upr_2\.mcp.json:14`), `code-index.exe` в `CODE_INDEX_HOME` нет (`ls .local/code-index`). Что демон не «не запущен», а снят снаружи и `daemon.json` устарел, подсказка не говорит; что запуск из сессии агента не переживёт перезапуск Claude, — тоже.

### Что проверено

- `crates/code-index-core/src/mcp/tools.rs:233–237`: `ToolUnavailable::DaemonOffline { message: "Демон code-index не доступен ({}). Запустите 'code-index daemon run' или Scheduled Task / systemd user unit." }`; `{}` — ошибка `client::path_status_async` (`client.rs`, `GET {} → {}`), при снятом процессе — отказ соединения на порт из `daemon.json`.
- Та же жёсткая команда ещё в двух местах: `tools.rs:223` (`NotStarted`: «вызовите 'code-index daemon reload'») и `daemon_core/client.rs:41` (`daemon_unavailable_hint`, нет `daemon.json`: «демон запущен — `code-index daemon run`»). `docs/operations.md:41–51` уже пишет `bsl-indexer.exe daemon …`.
- Собираются два бинарника с одним `cli.rs`: `code-index` (`crates/code-index/Cargo.toml:9–11`) и `bsl-indexer` (`crates/bsl-indexer/Cargo.toml:12–14`) — имя в тексте должно браться из `std::env::current_exe()`, как уже делает `detach_from_console_if_needed` (`cli.rs:1581`). Сервер MCP (`serve`) и демон на машине — один exe (`.mcp.json:14`, `daemon-run.cmd`).
- Признак «демон снят»: `runner.rs:765` `read_runtime_info()` даёт PID из `daemon.json`; живость PID — `lock.rs:64`, `is_process_alive` (приватная, `sysinfo`). 16.10 `daemon.json` остался от процесса, завершившегося без «демон остановлен» (`daemon.log:49686`).
- Тест сериализации `DaemonOffline` — `ipc.rs:224–232`; текста подсказки тесты не проверяют.

### Что менять

1. Помощник `daemon_core::client::daemon_command(sub: &str) -> String`: `"<current_exe> daemon <sub>"` (при ошибке `current_exe` — имя пакета `env!("CARGO_PKG_NAME")`); использовать в `tools.rs:223`, `tools.rs:235`, `client.rs:41`.
2. `tools.rs:233–237` — текст `DaemonOffline` из трёх частей:
   - причина: если `read_runtime_info()` есть и `lock::is_process_alive(pid)` (сделать `pub(crate)`) ложно — «демон PID <pid> (старт <started_at>) завершён без остановки, `daemon.json` устарел»; иначе — прежнее «не доступен (<ошибка>)»;
   - действие: «Запустите `<daemon_command("run")>` с CODE_INDEX_HOME=<путь> вне сессии агента (процесс, запущенный из сессии, завершится вместе с ней) или штатным запускателем машины (задача планировщика / автозагрузка / systemd user unit)»;
   - где причина отказа: «если демон не поднимается — строка ERROR в <CODE_INDEX_HOME>\daemon.log» (опирается на §1).
3. `docs/operations.md`, «Если MCP не отвечает»: абзац про устаревший `daemon.json` (PID не жив → демон сняли снаружи, запись «демон остановлен» в журнале отсутствует).

### Проверяемый результат

- Юнит-тест `tools.rs` (или `client.rs`): `daemon_command("run")` содержит имя файла текущего тестового exe и `daemon run`, не содержит литерал `'code-index daemon`; `grep -rn "'code-index daemon\|\`code-index daemon" crates/code-index-core/src` — 0.
- Юнит-тест текста `DaemonOffline` с `CODE_INDEX_HOME=<tmp>` и `daemon.json` с PID несуществующего процесса (например, `u32::MAX - 1`) → «завершён без остановки» и «daemon.log»; без `daemon.json` — прежняя ветка `daemon_unavailable_hint` с `daemon_command`.
- Живая проверка: остановить демон машины снятием процесса (не `daemon stop`), вызвать любой инструмент индекса → ответ `daemon_offline` называет `C:\Rusin\1c-agent-contour\.local\code-index\bsl-indexer.exe daemon run`, PID из `daemon.json` и путь `daemon.log`; затем поднять штатным запускателем.

## 3. Раскладка

После правок: `cargo test --workspace` зелёный; `CHANGELOG.md` и `CHANGELOG_EN.md`, раздел `[Unreleased]`, — одна запись со ссылкой на это ТЗ («Исправлено: причина отказа старта демона пишется в daemon.log; подсказка daemon_offline называет exe и устаревший daemon.json»). Выпуск `bsl-indexer` новой версии `1.0.1-ka.N`; доставка на машины — контуром: `python install/publish_bins.py --component code-index --version <версия>` (поднимает `CODE_INDEX_VERSION` в `.env`, кладёт `bin/bsl-indexer.exe`), затем `python install/update_code_index.py` на машине (останавливает демон, сохраняет прежний exe как `.bak`, ждёт ready всех путей). Раскатка `install_to_repo.py` в ka-upr и mdm для этого ТЗ не нужна: скиллы и шаблоны не меняются.

## 4. Решения владельца

1. **Негодный `index_dir` у одного пути — валить весь конфиг или только этот путь?** Сейчас `validate_entries` (`index_location.rs:9–28`) отклоняет весь `daemon.toml`, и 15.10 из-за одного пути (`mdm_obnovlenie-kontura`, `src/cfe`) встали все 29. При этом `runner.rs:76–78` уже держит правило «негодная настройка одного пути не должна мешать старту демона» для неразрешённого каталога индекса. Варианты: (а) оставить отказ целиком — §1 делает его видимым; (б) конфликтующие пути (оба участника дубля) не обслуживать, статус `error` с причиной в `/path-status`, остальные стартуют — нужна правка `parse_str`/`apply_config` и тест «один путь с дублем, остальные ready».
2. **Отвязывать ли демон от job-объекта родителя на Windows?** `detach_from_console_if_needed` (`cli.rs:1586`) ставит только `DETACHED_PROCESS | CREATE_NO_WINDOW`; если демон запущен из сессии агента, а родитель держит процессы в job с завершением при закрытии, демон умрёт вместе с ним. Что именно так сняли демон 16.10 01:08 — вывод ТЗ контура, здесь не проверялся. Варианты: (а) ничего не менять, подсказка §2 говорит «вне сессии агента»; (б) добавить `CREATE_BREAKAWAY_FROM_JOB` (0x01000000) с откатом на прежние флаги, если job запрещает выход (`spawn` вернёт отказ доступа), и проверкой на машине: демон, запущенный из сессии Claude, переживает её перезапуск.
3. **Писать ли причину отказа старта ещё и в отдельный файл** (`daemon.start-error` рядом с `daemon.json`), чтобы `check_env.py` контура и 021 («демон не поднялся за 30 с») показывали её без разбора журнала? Варианты: (а) нет, достаточно строки `ERROR` в `daemon.log` (§1); (б) да, файл пишется при отказе и удаляется при успешном старте — тогда отдельная строка в ТЗ контура для `check_env.py`.

- Приведение `daemon.toml` к одному блоку на путь — сделано в контуре (`78b265f`), повторять в code-index не нужно.
- Сами задачи 33–36 и их код (ka-upr, task-1713), загрузчик 021 — свои ТЗ (таблица выше); дефектов code-index в них, кроме двух пунктов выше, фидбеки не называют.
